# 前端代码审查

## 用途

当用户要求审查前端代码时使用此技能。触发后**必须**让用户选择以下四种审查模式之一：

### 模式选择（必须）

触发本技能后，先向用户确认审查模式（若用户已在指令中明确指定则跳过询问）：

> 请选择审查模式：
> 1. **指定文件** – 提供 1 个或多个文件路径
> 2. **指定目录** – 提供目录路径，扫描其下所有前端文件
> 3. **Git 暂存区** – 审查当前 `git staged` 的变更
> 4. **Git 版本号** – 审查指定 commit 引入的变更

### 模式 1：指定文件

用户提供 1 个或多个前端文件路径。

**执行步骤：**
1. 解析用户提供的文件路径列表（支持相对路径和绝对路径）。
2. 过滤出前端文件（`.tsx`、`.ts`、`.js`、`.jsx`、`.vue`），忽略非前端文件并告知用户。
3. 逐个读取文件完整内容，按审查清单执行检查。
4. 汇总所有文件的审查结果，按必需输出格式输出。

**示例触发：** "审查 `src/components/Button.tsx`"、"review `Header.tsx` 和 `Footer.tsx`"

### 模式 2：指定目录

用户提供目录路径，递归扫描该目录下所有前端文件。

**执行步骤：**
1. 使用 glob 匹配目录下的 `**/*.{tsx,ts,js,jsx,vue}` 文件。
2. 排除 `node_modules`、`dist`、`.next`、`build` 等构建产物目录。
3. 若文件数量超过 20 个，提示用户文件过多并列出文件列表，让用户确认或缩小范围。
4. 逐个读取并审查，按必需输出格式输出。

**示例触发：** "审查 `src/components/` 目录"、"review `pages/` 下的代码"

### 模式 3：Git 暂存区

审查当前 `git diff --cached` 的所有前端文件变更。

**执行步骤：**
1. 执行 `git diff --cached --name-only` 获取暂存区变更文件列表。
2. 过滤出前端文件（`.tsx`、`.ts`、`.js`、`.jsx`、`.vue`）。
3. 对每个文件执行 `git diff --cached -- <filepath>` 获取变更内容。
4. **仅针对变更行（diff）进行审查**，而非整个文件。若需上下文可读取完整文件辅助判断。
5. 汇总审查结果，按必需输出格式输出。

**示例触发：** "审查暂存区"、"review staged 代码"、"检查准备提交的代码"

### 模式 4：Git 版本号

审查指定 commit hash 引入的所有前端文件变更。

**执行步骤：**
1. 用户提供 commit hash（完整或短 hash 均可）。
2. 执行 `git diff <commit>^ <commit> --name-only` 获取该 commit 变更的文件列表。
3. 过滤出前端文件（`.tsx`、`.ts`、`.js`、`.jsx`、`.vue`）。
4. 对每个文件执行 `git diff <commit>^ <commit> -- <filepath>` 获取变更内容。
5. **仅针对变更行（diff）进行审查**，聚焦该 commit 引入的改动。
6. 汇总审查结果，按必需输出格式输出。

**示例触发：** "审查 `a1b2c3d` 这个提交"、"review commit `abc123`"、"看看这个版本的改动：`fe8d92a`"

对每个适用文件和模式，遵循以下清单。

## 审查清单

查看 [references/code-quality.md](references/code-quality.md)、[references/performance.md](references/performance.md)、[references/business-logic.md](references/business-logic.md) 获取按类别划分的动态清单——将其视为必须遵循的权威规则集。

标记每个规则违规时附加紧急程度元数据，以便后续审查者优先处理修复。

## 审查流程

1. 打开相关组件/模块。收集与类名、React Flow hooks、prop 记忆化和样式相关的代码行。
2. 针对每个审查点规则，记录代码偏离之处并捕获代表性代码片段。
3. 按照以下模板撰写审查内容。按 **紧急** 标志优先排序，然后按类别顺序（代码质量、性能、业务逻辑）分组。

## 必需输出格式

调用时，响应必须严格遵循以下两种模板之一：

### 模板 A（发现问题）

```
# 代码审查
发现 <N> 个需要修复的紧急问题：

## 1 <问题简要描述>
文件路径：<路径> 第 <行号> 行
<相关代码片段或指针>


### 建议修复
<修复建议的简要描述>

---
... （重复每个紧急问题）...

发现 <M> 条改进建议：

## 1 <建议简要描述>
文件路径：<路径> 第 <行号> 行
<相关代码片段或指针>


### 建议修复
<修复建议的简要描述>

---
... （重复每条建议）...
```

如果没有紧急问题，省略该部分。如果没有建议，省略该部分。

如果问题数量超过 10 个，总结为"10+ 个紧急问题"或"10+ 条建议"，仅输出前 10 个问题。

不要压缩段落之间的空行；保持原样以便阅读。

如果使用模板 A（即有问题需要修复）且至少有一个问题需要代码更改，在结构化输出后附加一个简短的后续问题，询问用户是否希望应用建议的修复。例如："是否需要我应用建议修复部分来解决这些问题？"

### 模板 B（无问题）

```
## 代码审查
未发现任何问题。
```
