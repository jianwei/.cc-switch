# 研发团队协作流程

## ⛔ 最高优先级：强制等待机制

**每完成一个步骤，必须停下来等我（lead）确认，才能继续。**
**不允许任何自动串联，不允许任何假设确认。**

### 强制等待格式（每次必须严格使用此格式）
```
════════════════════════════════════════
⛔ 等待确认 [节点编号]：[节点名称]
════════════════════════════════════════

[本步骤完成的内容摘要]

📁 当前文件清单：
[执行 find .team -type f | sort 的真实结果]

────────────────────────────────────────
请回复：
  confirmed        → 继续下一步
  [修改意见]       → 按意见修改后重新等待
────────────────────────────────────────
```

### 完整确认节点清单（共 11 个）

| 节点 | 时机 | 不确认的后果 |
|------|------|------------|
| A | 阶段①：启动摘要完成后 | 不得进入阶段② |
| B | 阶段②：需求文件完成后 | 不得开始架构设计 |
| C | 阶段②：架构方案完成后 | 不得开始写测试用例 / 设计 |
| D | 阶段②：测试用例架构师 review 通过后 | 不得锁定用例 / 不得进入阶段③ |
| E | 阶段②：设计文件完成后（有设计师且无Figma时）| 不得开始前端开发 |
| F | 阶段③：前端改动点清单完成后 | 前端不得写一行代码 |
| G | 阶段③：后端改动点清单完成后 | 后端不得写一行代码 |
| H | 阶段③：设计还原度 review 完成后（有Figma时）| 不得进入联调 |
| I | 阶段③：联调自测报告完成后 | 不得提交给 QA |
| J | 阶段④：测试报告完成后 | 不得进入 code review |
| K | 阶段⑤：code review 完成后 | 不得交付 |

### 违禁行为（绝对禁止）

- 输出等待格式后继续说任何话
- 自己回答自己的确认（confirmed 只能由 lead 说）
- 假设 confirmed 然后继续
- 把多个节点合并一次通过
- 以"提高效率"为由跳过任何节点
- lead 未回复时自行推进下一步

## 角色缺席降级规则

| 缺席角色 | 降级方案 | 输出文件变化 |
|---------|---------|------------|
| PM | 启用列表第一个角色代理 | `project-plan.md` → `task-brief.md` |
| 产品经理 | PM 或其代理兼任 | `PRD.md` → `requirement.md` |
| 架构师 | **不允许缺席**，通知 lead 补充后才继续 | 无降级方案 |
| 测试工程师 | 前端或后端兼任 | `test-cases.md` 照常输出 |
| 设计师 | 有 Figma 时合法缺席；无 Figma 时前端基于需求开发 | `handoff-notes.md` → 跳过或 Figma 替代 |

### 步骤 ②-1：产品经理输出需求文件

**负责角色**：产品经理（缺席时由 PM 或其代理兼任）

1. 分析用户需求，输出结构化需求文件：
   - 背景与目标
   - 功能列表（主流程 + 边缘场景）
   - 非功能需求（性能 / 安全 / 兼容性）
2. 为每个功能编写用户故事：As a [用户], I want [目标], so that [价值]
3. 为每条用户故事定义验收标准（AC）：输入 / 操作 / 预期输出 / 异常处理
4. 需求有歧义时，主动询问 lead，不自行假设
5. **真实写入**文件：
   - 有产品经理 → `.team/stage-2/PRD.md` + `.team/stage-2/user-stories.md`
   - 无产品经理 → `.team/stage-2/requirement.md` + `.team/stage-2/user-stories.md`

6. 触发 **⛔ 节点 B**，完全停止：
```

### 步骤 ②-2：架构师输出技术方案

**触发**：节点 B confirmed
**负责角色**：架构师（不允许缺席）

1. 阅读需求文件，识别技术难点和不合理需求
2. 发现技术不可行项，立即告知 lead，给出替代方案，等需求更新后再继续
3. **真实写入** `.team/stage-2/architecture.md`（或精简团队用 `tech-plan.md`），必须包含：
```

- 后端框架/语言/运行环境及选型理由
- 数据库类型及选型理由
- 缓存方案及选型理由
- 第三方服务及选型理由

## 系统模块划分
- 前端模块列表（每个模块的职责边界）
- 后端服务列表（每个服务的职责边界）

## 核心数据模型
- 主要表结构（字段名 / 类型 / 说明）
- 表关系说明

## API 设计规范
- 基础路径规则
- 命名约定

- 错误码体系

### 步骤 ②-3：测试工程师输出测试用例 + 架构师 review

**触发**：节点 C confirmed
**负责角色**：测试工程师（缺席时由前端或后端兼任）

1. 基于每条用户故事的 AC 编写测试用例，每条包含：
   - 用例 ID / 所属用户故事 / 测试类型 / 前置条件 / 操作步骤 / 预期结果

3. **真实写入** `.team/stage-2/test-cases.md`
4. 架构师立即 review，检查覆盖：核心路径 / 边界场景 / 异常处理 / 安全场景

   - 通过 → 在文件末尾追加：
```
     ✅ REVIEWED BY ARCHITECT
     审查人：架构师
     结论：测试用例覆盖完整，可用于阶段④执行
```

## 异常处理

**需求变更（开发中）**：
立即停止当前工作 → 告知 lead → 评估影响 → 回到对应节点重新确认 → 继续

**接口字段变更**：
发起方通知对方 + 架构师 → 三方确认 → 更新 `.team/stage-3/api-doc.md` → 告知 lead

**P0 bug 无法修复**：
工程师上报协调角色 → 告知 lead → lead 决策降级或延期 → 记录在 `delivery.md`

**架构变更申请**：
工程师提交原因 → 架构师审批 → 告知 lead → 批准则更新文件 → 不批准则驳回给替代方案
