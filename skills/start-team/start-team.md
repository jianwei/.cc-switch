# 启动研发团队

## 核心定义

**lead = 正在和我对话的用户，即你。**
**我（Claude）= 扮演所有已启用的 AI 角色。**

所有"等待 lead 确认"的节点，就是等待**你**在对话框里回复。
在你回复之前，我必须完全停止，不执行任何后续操作。

---

## ⛔ 强制停止机制

每个确认节点必须：

1. 把当前产出文件**真实写入磁盘**（不是只在对话里展示）
2. 执行 `find .team -type f | sort` 展示完整文件清单
3. 输出以下固定格式后**完全停止**，不再输出任何内容：
```
════════════════════════════════════════
⛔ 节点 [X/7]：[节点名称]
════════════════════════════════════════

[本节点产出摘要]

📁 当前文件清单：
[find .team -type f | sort 的结果]

────────────────────────────────────────
等待你的确认。
请回复：
  confirmed        → 继续下一步
  [修改意见]       → 我按意见修改后重新等待
────────────────────────────────────────
```

**违禁行为**：
- 输出上面格式后继续说任何话
- 自己回答自己的确认
- 假设 confirmed 然后继续
- 把多个节点合并一次通过

---

## 7 个强制确认节点

| 节点 | 时机 | 你需要确认的内容 |
|------|------|----------------|
| 1/7 | 阶段①完成后 | 角色分配、代理关系、执行计划是否正确 |
| 2/7 | 架构方案完成后 | 技术选型、模块划分、API规范是否认可 |
| 3/7 | 测试用例 review 完成后 | 知悉测试用例已锁定 |
| 4/7 | 改动点清单完成后 | 改动范围是否符合预期 |
| 5/7 | 联调自测完成后 | 联调报告是否通过 |
| 6/7 | 测试报告完成后 | 测试结果是否认可 |
| 7/7 | code review 完成后 | 最终质量是否认可，可以交付 |

## 执行规则

### 第一步：读取配置
- 流程：优先 `./.claude/workflow.md`，回退 `~/.claude/skills/team/workflow.md`
- 角色：依次查找 `./.claude/roles/{角色}.md` → `.patch.md` → `~/.claude/skills/team/roles/{角色}.md`

### 第二步：角色缺席代理

| 缺席角色 | 代理规则 |
|---------|---------|
| PM | 启用列表第一个角色代理 |
| 产品经理 | PM 或其代理兼任，输出 requirement.md |
| 架构师 | 不允许缺席，通知你补充后才继续 |
| 测试工程师 | 前端或后端兼任 |
| 设计师 | 有 Figma 时合法缺席；无 Figma 时前端基于需求开发 |

### 第三步：初始化目录（真实执行）
```bash
mkdir -p .team/stage-1 .team/stage-2 .team/stage-3 \
         .team/stage-4 .team/stage-5 .team/stage-6
```

执行后输出：
```
✅ 目录初始化完成：
.team/
├── stage-1/
├── stage-2/
├── stage-3/
├── stage-4/
├── stage-5/
└── stage-6/
```

### 第五步：你 confirmed 后按阶段执行

每个阶段严格遵守：

1. **先写文件到磁盘**，再在对话里展示摘要
2. **执行** `find .team -type f | sort`
3. **输出节点格式，完全停止**
4. **等你回复**，不做任何假设

文件写入方式（每次都要真实执行）：
```bash
cat > .team/stage-X/文件名.md << 'CONTENT'
[文件内容]
CONTENT
```
