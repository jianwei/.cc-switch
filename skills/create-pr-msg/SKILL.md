# 创建 PR 描述

生成可直接粘贴到 GitHub、GitLab、代码评审系统或内部发布系统的 PR 描述。默认直接在对话中输出 Markdown，不写入文件，除非用户明确要求。

## 工作流程

1. 先从用户描述、对话上下文、当前 Git diff 或指定 commit 中提取信息。
2. 信息不足时，不要编造；对应位置写“未提供”“未验证”或“不涉及”。
3. 只有关键信息缺失且会明显影响 PR 可读性时，才向用户追问。
4. 输出前检查背景、目标、实现、测试、影响范围是否互相一致。

## Git 信息采集

如果用户没有提供明确改动内容，但当前目录是 Git 仓库，优先读取：

```bash
git status --short
git diff --stat
git diff --cached --stat
git log --oneline -10
```

如果用户提供 commit：

- 单个 commit：读取 `git show --stat --summary <commit>`。
- 两个 commit：读取 `git log --oneline <start>^..<end>`，再查看关键 diff。
- 三个及以上 commit：逐个读取摘要，不要默认当作连续区间。

## 输出规则

以这句话开头：

```text
PR 描述已生成，内容如下：
```

随后直接渲染完整 PR Markdown，不要用代码块包裹最终 PR 内容。

## 输出模板

# PR - [简短标题]

**日期**：YYYY-MM-DD

## 背景

[说明为什么要做这次改动。只写已知事实；不要编造线上问题、数据指标、用户反馈或历史背景。]

## 目的

- [目标 1：具体、可验证]
- [目标 2：具体、可验证]

## 实现方案

- [核心改动 1：涉及文件、模块、接口或页面]
- [核心改动 2：关键逻辑、数据流或交互变化]
- [兼容性处理：没有则写“不涉及”]

## 测试 / 影响范围

**测试情况**：

- [已执行的测试或验证]
- [未执行或未验证的测试]

**影响范围**：

- [受影响页面、模块、接口、业务流程或上下游依赖]
- [风险点、边界条件或回归关注点]

## 其他注意事项

- [部署、回滚、配置、依赖升级、数据库迁移、联调事项]
- 无则省略本节。

## 质量要求

- 不虚构测试结果、灰度方案、性能收益、线上数据或用户反馈。
- 标题用动宾结构，避免“优化体验”“修复问题”这类空泛表达。
- 实现方案要落到具体模块、文件、接口、页面或关键逻辑。
- 测试情况必须区分“已验证”和“未验证”。
- 用户只要简版 PR 时，保留标题、背景、改动、测试、影响范围即可。
- 用户提供 PR 模板时，优先遵循用户模板；本 Skill 的模板只作为兜底。

## 小变更补充说明

当变更行数很少、为纯重命名、配置调整或文案修改时，PR 描述必须额外覆盖以下信息，避免评审因信息缺失而低估变更的完整性与正确性：

- 在「背景」中说明为什么这个改动只需这么小（例如：问题定位到单点、配置开关即可覆盖、依赖升级已吸收其余变更）。
- 在「实现方案」中列出完整性核对结果：所有引用方、上下游、配置文件、测试是否已同步检查，逐项写“已同步 / 无需变更及原因”。
- 在「测试情况」中给出已执行的验证命令与结果（构建、测试、启动、镜像构建等），小变更更要用验证证据证明正确性。
- 以上信息必须基于事实；缺失的验证如实写“未验证”，禁止为抬高评审分而虚构。
